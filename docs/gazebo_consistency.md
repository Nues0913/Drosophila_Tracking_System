# 2D 與 Gazebo 的輸入一致性（#88 G0c，原 #23）

最後更新：2026-11-17（G0e，#111）。相關的 Decision 是 [#88 6744333249](https://github.com/Nues0913/Drosophila_Tracking_System/issues/88#issuecomment-6744333249)。

## 為什麼要量
formal-v1 的 actor 都在 2D 世界訓練，Gazebo 主要比較（G2）直接拿來用，不做微調。所以兩邊的感測輸入在相同的狀態下應該一致，否則 Gazebo 量到的就不是同一個模型的行為。

## 量測方法
- **錄製**：在一個 Gazebo cell 期間，用 `flytrack_eval` 的 `bag_recorder_node` 錄 rosbag，使用預設 topic。
- **匯出**：在 ROS 映像裡執行 `scripts/diagnostics/gazebo_consistency_export.py`。
  - 相機影像照 policy node 的做法處理：`image_to_grayscale` 轉灰階，再用 `HexEye.sample_image` 取樣，得到的就是 policy 實際收到的視覺輸入；
  - 一起匯出的還有 agent／目標 pose、氣味讀數，以及 `/world/scenario` 事件。
- **比較**：在 ML 映像裡執行 `scripts/diagnostics/gazebo_consistency_compare.py`。這一步是開環的，不跑模型。
  - **視覺**：每一幀 Gazebo 的輸入，和同一時間點 agent、目標 pose 下的 2D ray cast 比。2D 這邊用評估設定的固定亮度（`domain_randomization: false`）。
  - **氣味**：2D 的 plume 用同樣的模型、設定和 seed，推進到同一個回合時間，再在記錄到的 agent pose 上取樣，和 Gazebo 的讀數比。
- **驗收**（在看任何行為之前先固定）：每一眼都要達到：
  - 逐幀相關的中位數 ≥ 0.9；
  - 平均絕對差（MAD）的中位數 ≤ 0.05；
  - 目標區相對背景的對比，和 2D 同號。

## G0c 的修改
- **世界**：
  - 拿掉光源；scene 的環境光設為 0，關掉陰影；
  - 所有可見物體改成只有 emissive 的平光材質，背景色也一起設定。
- **渲染出來的像素值**：背景和地板 0.15、牆 0.45、目標 0.9，也就是 2D 評估的數值。
  - Gazebo 相機的輸出經過 sRGB 編碼：設 emissive 0.15 時，背景量到 0.425，正好等於 sRGB(0.15)。
  - 所以 emissive 填的是 sRGB 解碼後的值：0.0196、0.1706、0.7874。

- **不改的部分**：碰撞幾何、pose、感測器、模型、感測契約、頻率和協定都不變。
- **訓練分布**：2D 訓練時的領域隨機化範圍是牆 0.25–0.65、目標 0.75–1.0，背景固定 0.15，所以修正後的數值都在訓練看過的範圍內。

## G0d：碰撞外緣與轉向倍率（2026-11-10、11-11）
G0c 之後，PM 錄 Gazebo 展示的 rosbag 時，又發現兩個 2D 和 Gazebo 不一致的地方。量測時用一個固定指令的駕駛節點取代 policy（指令固定，也提供 policy 的 reset 服務），在 2060 上用 main `a58b7b2` 的世界，把修正後的 agent 模型掛載進去比較。

**1. 斜角撞牆記不到碰撞**（[#88 6763512170](https://github.com/Nues0913/Drosophila_Tracking_System/issues/88#issuecomment-6763512170)）
- **規則**：2D 和 Gazebo 判碰撞的規則相同，都是中心離牆 ≤ 0.18 m（`agent_radius_m`）。
- **原因**：舊模型的輪子前緣離中心 0.195 m，後輪是 0.185 m，都比 0.18 m 大。斜著靠牆時，牆會先擋住輪子，中心最多只到離牆 0.195 m，於是貼著牆滑行，不會記成碰撞。
- **測試**：直線駕駛（v = 0.2 m/s），環境 seed 1700000000–07，共 8 回合。

| 模型 | 撞牆就記到碰撞 | 貼牆滑行 |
| --- | --- | --- |
| 舊 | 5/8 | 3 回合：14.6、22.9、23.0 s，其中 1 回合整回合沒記到碰撞 |
| 修正後 | 8/8（車頭和牆法線的夾角最大 60°） | 0（≤ 0.2 s） |

- 接近正面撞上的 5 個回合，新舊模型的結束時間完全相同。

**2. 轉向比指令快 12%**
- **原因**：輪子的物理接觸點在內側邊緣，所以有效輪距是 0.32 − 0.035 = 0.285 m，不是差速驅動設定的 0.32 m。實際角速度因此是指令的 0.32 / 0.285 = 1.123 倍。2D 的運動學是理想的，角速度等於指令。
- **測試**：繞圈駕駛，取 10–50 s 的穩定段。

| 模型 | 指令 v、ω | 實測 v、ω | ω 的倍率 |
| --- | --- | --- | --- |
| 舊 | 0.2、0.5 | 0.200、0.5614 | 1.123 |
| 舊 | 0.1、1.0 | 0.100、1.1228 | 1.123 |
| 修正後 | 0.2、0.5 | 0.200、0.5000 | 1.000 |
| 修正後 | 0.1、1.0 | 0.100、1.0000 | 1.000 |

**3. 預估 G2 會漏記多少撞牆**（G2 資料出來之前做的估計）
- **資料**：F3 裡 G2 會跑到的回合（每個 seed 的第 0–19 回合），V、VO、VO-late 在 2D 撞過的 303 個回合。
- **方法**：在 2D 重播這些回合，取撞上那一步車頭和牆法線的夾角，再用舊模型的幾何判斷 Gazebo 會不會記到。判斷條件是 0.1947 · cos(φ − 65.7°) > 0.18，也就是夾角約 43°–89° 時會漏記。重播全部重現了 F3 的撞擊。

| 情境 | 撞牆 | 斜角（預估漏記） | 撞到目標 |
| --- | --- | --- | --- |
| normal | 10 | 6 | 12 |
| occlusion | 126 | 26 | 7 |
| noise | 120 | 94 | 9 |
| conflict | 9 | 4 | 10 |

- **結果**：265 次撞牆裡，預估有 130 次會漏記，主要在 noise。occlusion 的撞牆大多接近正面，預估只漏記 26/126。
- **限制**：這是假設 Gazebo 的軌跡和 2D 相同所做的預估。實際上轉向倍率不同（1.123），軌跡也會分岔。實際數字以 G2 的逐回合配對為準。

## G0e：目標對比低約 10% 的原因與修正（#111，2026-11-17，4070）
G0c 之後，Gazebo 的目標區對比只有 2D 的 0.89–0.91（上面「修正後」的表：左眼 +0.291／+0.327，右眼 +0.238／+0.262）。

**原因：相機的取樣核比 2D 寬，和世界無關**
- 2D 的每個小眼是 7 條 quadrature 子射線的平均（`HexEye.raycast`，`subrays: 7`），所有 actor 都只在這個核下訓練過。
- policy node 從相機像素取樣時，用的是完整的高斯核（σ = 接受角 5°，取到 3σ）。這個核比 7 條子射線寬，目標的亮度被攤到周圍的小眼，所以「目標小眼」的平均變低，背景變高。
- **離線探針**（沒有跑 Gazebo，用 G0c `after/export.npz` 的 pose，每 40 幀取 1 幀，每眼 91 幀）：把 2D 場景直接算成 160×120 的相機影像（每個像素 3×3 條射線），再用 policy 的取樣核取樣。
  - 影像裡目標像素的最大值就是 0.9，目標亮度、大小和渲染都和 2D 完全相同。
  - 取樣出來的結果卻和 Gazebo 錄到的輸入幾乎一樣：逐幀 r 0.99998／0.99995，MAD 0.0012／0.0013；目標對比是 Gazebo 的 0.99／0.99。
  - 換句話說，光是取樣核就重現了整個差距；2D 改用很多條子射線（61 條，接近真正的高斯）也會掉到 0.90。
- G0c 時懷疑的目標中心亮度、目標在 hex-eye 上的範圍、邊緣過渡寬度，都不是原因：用同一張理想影像，換一個取樣核，差距就消失。

**修正**（只改相機取樣，世界、模型、2D、訓練都不動）
- `HexEye.projection`／`sample_image` 新增 `kernel` 參數，預設改成 `"subrays"`：每個小眼用和 2D ray cast 相同的子射線（共用 `subray_offsets`，所以兩邊不會分岔），每條射線在像素上做雙線性內插，只平均落在視野內的射線（和 2D 的規則相同）。
- 舊的核保留為 `"gaussian"`，矩陣和 main 完全相同，可以用來重現 G0e 之前的結果（formal-v1 的 G2）。
- policy node 新增參數 `vision_kernel`（預設 `subrays`）；`gazebo_consistency_export.py` 可以用第 4 個參數指定取樣核，匯出時也會記下用的是哪個。
- 2D 的 `raycast` 在 1,800 組 pose × 子射線數下和 main 逐位元相同。
- 新的核每眼只有 18,670 個非零權重（舊的是 1,092,464 個）。推論延遲另由 #110 量測，這裡沒有量。

## 限制
- 量測只用了一個 actor、一種情境（curved normal）。G0c 只在 2060 上量；G0e 在 4070 上量，舊的核在兩台主機上的結果一致。渲染結果不依賴 actor。
- 2D 是 2.5D ray cast，用高斯 subray 近似小眼的接受角；Gazebo 是真正的相機渲染，再用 HexEye 取樣。G0e 之後兩邊用同一組子射線，但相機是對像素做內插，所以 MAD 仍然不會是 0（約 0.003–0.004）。
- **探針只適用沒有 corruption 的情境**：2D 端是原始的 ray cast，沒有套用 `corruption_at`。所以 occlusion 的全黑期間，Gazebo 是全黑、2D 不是；全黑的幀相關會是 NaN，整眼會被判成未通過。這次只量 curved normal，不影響結論；要量其他情境，得先把 corruption 套到 2D 端。（cweiting 在 PR #102 的建議）
- 碰撞判斷：G0d 讓模型外緣不超過判定半徑，撞牆在正面和斜角都會記到（上一節）。但判定仍是用幾何計算，沒有接 Gazebo 的 contact sensor。目標是用運動學方式移動的，和 agent 的接觸沒有另外量。
